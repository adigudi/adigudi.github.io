Returns Defect Triage System

One agent reads every return, grades how likely it is to be a production defect, and feeds four different teams the view each one actually needs. Warehouse gets a work queue. Quality gets batch intelligence. Sourcing gets a credit ledger. Leadership gets one number.

All data below is synthetic, written by me to stress-test the logic and deliberately defect-heavy so the interesting cases are visible. No Cuts data was used. Vendor names are invented. Point the same engine at a real returns export and these screens fill with live data.

The join that makes it work

A return knows its SKU. It does not know which production batch that unit came from, and without that you can grade defects but never attribute them to a vendor or a run.

return → sku → batch → vendor

Resolved by order date against production receipt windows. This is the single most fragile link in the pipeline and the first thing I would want to look at in real data, because if batch attribution is wrong, every vendor claim is wrong.

Grading step

Input
Reason code, customer comment, inspector note, condition photos, and the SKU's spec sheet, assembled into one context per return.
Output, schema-validated
defect_likelihood 0-100, defect_category from a fixed list, rationale one sentence, evidence_used.
Idempotency
Results cached by rma_id and input hash, so a re-run never re-grades or re-bills. Re-grading only happens if the inspector edits the note.
Failure handling
A malformed or low-confidence response routes to human review rather than defaulting to a score. The system never guesses toward a vendor claim.

Data quality gates

Where the pipeline deliberately stops rather than producing a confident wrong answer.

  • No photo, no auto-claim. A return without usable images can be graded from text but never auto-flagged for a vendor credit, because the claim would not survive a vendor pushing back.
  • Unknown batch blocks attribution. If the SKU cannot be resolved to a batch, the defect still counts in quality totals but is held out of the vendor ledger and raised as a data fix.
  • Reason-code drift. Reason codes get renamed and added by whoever manages the returns app. Unmapped codes raise an alert instead of silently falling into a default bucket.
  • Claim reconciliation. Credits claimed are matched against credits actually received. A widening gap is the signal that the whole system is being ignored by a vendor.
  • Duplicate returns. Reopened or re-shipped RMAs are deduplicated on rma_id so a single defective unit is never claimed twice.
What this demo is, and is not. These screens run on synthetic data to show the grading engine and the four views it feeds. The full build is the plumbing: connectors to the four source systems, the batch attribution job, evidence filing to Drive, the persistent credit ledger, the weekly vendor sends, and the escalation hooks. That wiring is scoped against real systems, which is the conversation worth having.
